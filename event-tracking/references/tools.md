# Tool notes

How the rules in [SKILL.md](../SKILL.md) map onto each analytics tool. Read the section for every
tool the project sends to, plus [Every tool](#every-tool). Vendor details change. When a note here
disagrees with the tool's current docs or its `--help`, trust the docs and say so in the report.

## Every tool

- **Event names are case-sensitive everywhere.** `Account Is Created` and `account is created` are
  two events. The typed module (SKILL.md step 4) is what prevents this.
- **Server SDKs batch events.** In serverless functions, scripts and short-lived workers, events
  still queued when the process freezes or exits are lost without any error. Await a flush before
  the response returns. Shut a client down only when it was created for this one request, because
  warm invocations reuse a module-level client. The per-tool calls are in each section below.
- **Autocapture and retroactive tracking** (Heap, PostHog autocapture, Amplitude autocapture) suit
  exploration. Any event that a stated question or an automation depends on still gets a named
  event in the plan. Selector-based definitions break without warning when the markup changes.
- **A CDP fans out.** With Segment or RudderStack in front, the name and properties are set once
  and every destination receives them. Check the destination list before sending anything
  sensitive (the personal-data rules).
- **Tool-defined events.** When a tool or CDP spec reserves a name that unlocks a feature (GA4's
  `purchase`, Segment's e-commerce spec `Order Completed`), keep that name and its parameters for
  that behaviour, and note the exception in the plan. Every other event follows the naming scheme.

## Amplitude

- **Names:** Title Case with spaces is stored as written. Amplitude Data can enforce a casing rule
  for the whole project.
- **Plan home:** Amplitude Data. Events, properties, property groups and descriptions live there.
  Sources (Web, iOS, Backend) are first-class. With Ampli, add the event to the plan and to its
  source, then run `ampli pull` to regenerate the typed wrapper. `ampli status` checks that every
  planned event is called in the code.
- **Types:** string, number, integer, boolean, enum, const, array, object. Use array-of-object
  properties only for item-level analysis such as carts: Amplitude splits out one level of child
  properties, and each counts toward the event property limit.
- **Limits:** 2,000 event types and 2,000 event properties per project. Past that, new ones stop
  being queryable. Names with parameters in them burn through this.
- **Identity and accounts:** `setUserId` on the client, `user_id` on server events. Account-level
  analysis needs the Accounts add-on; in a B2B product, check whether the project has it. Pass the
  account in each event's `groups` field, or call `setGroup` again on every workspace switch,
  because it sticks to the user until changed. Set account properties with `groupIdentify`.
- **Serverless:** `await client.flush().promise` in the Node SDK before returning.
- **Verify:** set the Browser SDK `logLevel` to Debug, then check User Lookup or the Event Explorer
  extension.

## PostHog

- **Names:** any string. PostHog's own docs suggest a different convention. Follow the scheme in
  SKILL.md unless the project has already settled on another (then ask; see the migration
  section). Names and properties starting with `$` are reserved for PostHog.
- **Plan home:** event and property definitions (descriptions, tags, verified status) under Data
  management. Schema management is experimental: it adds typed property groups attached to events,
  with TypeScript types generated by `posthog-cli exp schema pull`. Commit `posthog.json` and the
  generated file. PostHog's Definitions (`npx posthog-definitions apply`) manages event definitions
  and property groups as code, and its `createTypedPostHog` wraps the client to type-check every
  `capture` call, which can be the typed module of step 4. These are new and changing quickly, so
  check the current docs for command names. Without them, the repo's plan file and typed module
  are the schema.
- **Types:** string, numeric, boolean, datetime. PostHog infers the type from the values it first
  receives. It can be corrected in Data management, but charts built in the meantime break, so
  send the right type from day one.
- **Host:** `posthog-node` defaults to the US cloud. When `posthog-js` sends to the EU cloud
  (`eu.i.posthog.com`) or a self-hosted instance, set the server client's `host` to match, or the
  server events land in a different project.
- **Sources:** no source concept. Send a const `eventSource` property, or use separate projects
  for truly separate products.
- **Identity and accounts:** `posthog.identify(userId)` on the client. Server events need a
  `distinctId` equal to that same ID. Group analytics is a paid add-on, billed on every identified
  event in the project once it is enabled, with up to 5 group types per project. Use
  `posthog.group('company', accountId, traits)` on the client, and call it again when the user
  switches workspace. Pass `groups: { company: accountId }` on every server call, and set account
  properties from the server with `groupIdentify`.
- **Serverless:** create the client with `flushAt: 1, flushInterval: 0` and `await
  client.flush()` before returning, or use `captureImmediate` where the installed `posthog-node`
  version has it. For a client created per request, `await client.shutdown()`.
- **Verify:** `posthog.debug()` in the browser, then the Activity (live events) view.

## Mixpanel

- **Names:** any string. Names and properties starting with `$` or `mp_` are reserved.
- **Plan home:** Lexicon holds descriptions, display names and tags. The Lexicon Schemas API
  accepts JSON Schema (draft-07) per event, so a plan file in the repo can be synced into it.
- **Types:** string, numeric, boolean, date, list, object and list of objects. Lists of objects
  work as filters and breakdowns in core reports, but Lexicon can't describe the keys inside
  them. Use them only for a question that needs item-level breakdowns.
- **Sources:** no source concept. Send a const `eventSource` property.
- **Identity and accounts:** `mixpanel.identify(userId)` on the client and the same value as
  `distinct_id` on the server. Group Analytics is a paid add-on, and its group key (such as
  `company_id`) must be defined in project settings. The key is an ordinary event property: an
  event without it can't be attributed to an account, and a user profile property doesn't count.
  `set_group('company_id', accountId)` adds the key to every later event from that browser, so
  call it again on every workspace switch. Server events set the key themselves. Account
  properties go on the group profile (`get_group(key, id).set(...)`).
- **Serverless:** the Node library sends each `track` as its own request, so await its callback
  before returning.
- **Verify:** `debug: true` in `mixpanel.init`, then the Events view.

## Segment and RudderStack

- **Names:** any string. Segment's own spec uses `Object Action` Title Case (`Order Completed`).
  Keep spec names only where a destination maps them (see Every tool).
- **Plan home:** Protocols tracking plans (a paid Segment add-on), or RudderStack tracking plans.
  Both validate events against JSON Schema and can block events that don't conform. Segment's
  Typewriter generates typed clients from the plan but is no longer actively developed; prefer a
  hand-written typed module unless the project already uses it.
- **Sources:** first-class, one per runtime or codebase. These are the sources the rules describe.
- **Identity and accounts:** `identify(userId, traits)`, and `group(accountId, traits)` for
  accounts, with account properties as the group traits. Most destinations map `group` onto
  their own account entity. Call it again when the user switches workspace. Server calls take
  `userId` and, for accounts, `context.groupId` or the destination's own mapping. Whether the
  destination can analyse accounts is that destination's question (see its section).
- **Serverless:** `await analytics.closeAndFlush()` for a per-request client, or `flush()` on a
  shared one.
- **Verify:** `analytics.debug(true)`, then the source's Debugger tab.

## Google Analytics 4

- **Names:** letters, digits and underscores only, starting with a letter, 40 characters at most.
  Write the scheme's words in snake_case: `account_is_upgraded`. Prefixes `ga_`, `google_` and
  `firebase_` and the automatically collected event names are reserved. Where GA4 has a
  recommended event for the behaviour (`sign_up`, `login`, `purchase`), use it, since its reports
  depend on that name.
- **Properties:** snake_case parameters, to match GA4's own (`count_projects`). There are limits
  on the number of parameters per event and on value length, and over-long values are cut
  without warning. Check the current numbers in Google's docs. A custom parameter shows in reports
  only after it is registered as a custom dimension or metric, so list each registration as a
  human step in the report.
- **Plan home:** none in GA4. The repo's plan file and typed module are the schema.
- **Identity:** set `user_id` on the config or event when the user is known. GA4 has no account
  entity: send `account_id` as an event parameter, registered as a custom dimension. For
  account-level analysis, export to BigQuery or use another tool. Server events go
  through the Measurement Protocol and need the browser's `client_id` to join a session.
- **Verify:** DebugView, with `debug_mode: true` or Tag Assistant.

## Heap

- **Names:** custom events via `heap.track(name, properties)`, any string. Most of Heap's events
  are defined retroactively from autocapture (see Every tool).
- **Properties:** flat scalar values (string, number, boolean). Send nothing nested.
- **Identity and accounts:** `heap.identify(userId)`. Account properties come through
  `addUserProperties` or Heap's account integrations.
- **Verify:** the Live data feed.

## Anything else

For a tool not listed (June, Pendo, Snowplow, a home-grown pipeline), answer these from its docs
before designing:

1. What characters and length can an event name and a property name hold? Map the scheme onto
   that form.
2. Does it validate a schema? If so, the plan lives there. If not, the repo's plan file and typed
   module are the schema.
3. Can it filter on nested values? Assume not.
4. How does it join client and server events for one user and one account?
5. What is its debug or live-event view for step 5?
